# Demo 项目 I/O 性能优化待办清单

## 1. 问题背景

当前 `search_mode` 在处理查询时，CPU 利用率受限于磁盘 I/O 等待，峰值仅约 200%，远未达到多核硬件的潜力（如 800%）。核心瓶颈在于查询的两个阶段：
1.  **索引加载**：当所需 bucket 索引（Vamana, bq, bqgraph）未命中缓存时，需要从磁盘同步读取。
2.  **真距复排**：需要从 `base.fbin` 文件中读取原始向量，此过程涉及大量随机读。

为解决此问题，我们提出以下两方面的优化策略，旨在最大化 CPU 利用率，提升 QPS。

## 2. 优化方向一：减少 I/O 请求 (缓存 / 批量 / 合并)

### 2.1. 缓存策略深度优化 (Enhance Caching)

**现状**: Demo 已为 BQ 产物和 Vamana 子图提供了基于 LRU 的非阻塞缓存。

**待办事项**:
- **[ ] 任务 1: 实现更智能的缓存淘汰策略**
    -   **描述**: 当前的 LRU 策略未考虑缓存对象的大小或访问频率。可探索实现 LFU (Least Frequently Used) 或带大小权重的 LRU (Size-Aware LRU)，优先缓存更小、更频繁访问的 bucket，提高缓存效率。
    -   **收益**: 在有限的缓存预算下，提升高价值 bucket 的命中率。

- **[ ] 任务 2: 实现跨查询的向量缓存 (Vector Cache for Reranking)**
    -   **描述**: 在真距复排阶段，不同查询可能会重复读取相同的热门向量。可以设计一个专用的向量缓存，存储从 `base.fbin` 读取出的高频向量。
    -   **收益**: 显著减少热门向量的重复磁盘读取，尤其在数据分布不均的场景下。

### 2.2. I/O 请求合并优化 (Optimize Request Batching)

**现状**: 复排阶段已实现基于 `O_DIRECT` 的单查询内请求合并（gid 排序 + 批量 `pread`）。

**待办事项**:
- **[ ] 任务 3: 实现跨查询的全局 I/O 批处理 (Cross-Query I/O Batching)**
    -   **描述**: 设计一个全局 I/O 调度器。多个查询线程将它们的向量读取请求（gids）提交给调度器，而不是自己直接读取。调度器聚合来自多个查询的 gids，进行全局排序和合并，形成更大的、更连续的 I/O 请求批次，然后交由 I/O 线程处理。
    -   **架构**:
        1.  查询线程：提交 `(query_id, [gids])` 请求到全局队列。
        2.  I/O 调度线程：定期从队列拉取请求，聚合 gids，执行最优的批量读取。
        3.  查询线程：等待 I/O 完成并取回自己的向量数据。
    -   **收益**: 将多个查询的小随机读合并为极少数的大顺序读，最大化磁盘吞吐量，极大降低 I/O-wait。

## 3. 优化方向二：并行与异步 I/O

### 3.1. I/O 线程池 (I/O Thread Pool)

**现状**: 查询线程自己执行同步的 `pread` / `read` 操作，计算与 I/O 耦合。

**待办事项**:
- **[ ] 任务 4: 解耦计算与 I/O，引入专用 I/O 线程池**
    -   **描述**: 创建一个独立的 I/O 线程池（线程数可配置，如 4-8）。当查询线程需要读取数据（索引或向量）时，它向线程池提交一个 I/O 任务并返回一个 `std::future`。查询线程可以继续处理其他已就绪的任务（如果架构支持），或等待 `future` 完成。
    -   **实现**:
        -   使用 `std::async` 或自定义的 `ThreadPool` 类。
        -   I/O 线程负责执行 `pread` 等阻塞操作。
        -   计算线程（查询线程）从 I/O 线程中解放出来，只要有就绪数据就可以持续工作。
    -   **收益**: 实现了计算和 I/O 的并行，当一个查询在等 I/O 时，CPU 可以去处理另一个已完成 I/O 的查询，提升总体资源利用率。

### 3.2. 现代异步 I/O: `io_uring` (Linux Only)

**现状**: 使用同步的 `pread`，即使在 I/O 线程池中，线程在等待 I/O 时也会被内核阻塞。

**待办事项**:
- **[ ] 任务 5: 集成 `io_uring` 实现全异步 I/O**
    -   **描述**: 对于 Linux 环境，将底层的 `pread` 调用替换为 `io_uring` 异步接口。这是目前最高效的 I/O 模型，可实现零 syscall 开销的 I/O 提交与完成。
    -   **实现**:
        1.  初始化 `io_uring` 实例，并由一个或多个 I/O 线程管理。
        2.  查询线程需要数据时，构建一个 `io_uring` 提交队列项（SQE），包含读操作信息和回调（或 `future`）。
        3.  I/O 线程提交请求给内核，然后可以立即处理其他事务，无需等待。
        4.  I/O 线程通过查询完成队列（CQE）获取已完成的 I/O 结果，并通知上层查询线程。
    -   **收益**: 单个 I/O 线程就能管理极高并发的 I/O 请求，将线程从阻塞等待中彻底解放，实现极致的 I/O 性能和最低的上下文切换开销。

## 4. 实施建议与优先级

1.  **短期 (验证与调优)**:
    *   **确认并调优现有参数**: 确保 `RERANK_O_DIRECT=1`, `RERANK_USE_MMAP=0` 已启用。精细调整 `BQ_*_CACHE_MB`, `RERANK_BATCH_*`, `RERANK_GAP_GIDS` 等参数，找到当前硬件下的最佳配置。开启 `BQ_PREWARM_TOP` 预热缓存。

2.  **中期 (架构改进)**:
    *   **实施 I/O 线程池 (任务 4)**: 这是最通用且效果显著的优化。它将计算和 I/O 分离，是提升 CPU 利用率的关键一步，且跨平台兼容性好。

3.  **长期 (极限性能)**:
    *   **实施跨查询批处理 (任务 3)**: 与 I/O 线程池结合，可将复排阶段的 I/O 效率推向极致。
    *   **集成 `io_uring` (任务 5)**: 如果部署环境为现代 Linux 内核，这是实现最终 I/O 性能的理想选择。

通过上述优化，有望将 CPU 从 I/O 等待中解放出来，使其利用率达到硬件上限，从而大幅提升 Demo 的查询吞吐量。
