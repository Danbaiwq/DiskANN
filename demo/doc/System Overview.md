# System Overview

## S.1 多次小样本并行 Kmeans

ANNS 中 IVF 等基于桶改进的向量索引方法通过单轮采样 10%～20% 的数据量用于聚类，之后再基于该聚类结果划分数据集，其生成的聚类质量取决于单轮采样的数据质量，如果采样数据集的数据分布与原数据偏离较大，或是原数据集的数据分布特别不均匀，会导致聚类效果非常差；并且随着数据量增加，其仍需要预留大量的内存空间用于存放训练数据集，如在 1B 数据集中采样 10% 需要至少存放 100M 的向量内存空间，这两个缺陷说明单轮采样的聚类训练方法不仅造成高的内存成本，还有可能由于采样不均导致聚类结果质量较差。

<流程图>

LiteANN 通过从原数据中采样多次 1% 的数据集，分配给独立批计算单元用于聚类训练，其中计算单元数与采样次数相同，每个计算单元内有相同数量的进程。在得到这多个计算单元训练得到的中间聚类结果后，再进行一次集中式聚类，从而得到最后的聚类。通过多次采样原始数据集，能学习到原始数据集的更详细的数据分布特征；通过将采样数据集分配给指定的进程计算单元，最大程度地利用了系统的可计算能力。

得到聚类质心后，为减少边缘向量的访问漂移，LiteANN 将原始数据依次分配到距离其最近的 L 个聚类桶内，同时为了避免向量的冗余分配，计算向量与最近桶的距离为 l，和向量与其他 L-1 个桶质心的距离 l'，按照 RNG 性质，仅分配到满足 alpha*l > l' 的桶内。

同时，为避免单个桶内向量数量过多，导致内存无法容纳单桶构图和单桶查询，LiteANN 仅对限制桶内向量数量的最大值，既控制了构建和查询时需要的内存空间，同时避免向量由于平衡限制被漂移到更不相关的桶内，根据实验得到的经验阈值为 L * N/ M.

## S.2 图桶混合量化索引

在所有向量通过 RNG 限制的边缘处理分配到相应桶内后，根据动机 2 对比桶搜和图搜的实验，LiteANN 在构建索引前会采样 50K 向量，以 10K 为间隔分组对比桶搜和暴搜的性能确定边界阈值 T 后，如果桶内向量数量大于 T，则用桶内向量数据构建图索引；如果桶内向量数量小于等于 T，则仅进行量化处理后构建桶索引。查询时则根据桶内索引进行图遍历或线性扫描。

### S.2.1 索引构建

为进一步减少查询时所需的内存空间，LiteANN 构建索引时对各桶内向量进行了 BQ 量化，其中不同桶内 BQ 量化的原点坐标为桶内质心，虽然 1-bit BQ 能将向量压缩至 8x-32x，但考虑到量化程度越高，越需要用更大的候选池进行复排，从而增加磁盘访问的次数，根据实验经验，LiteANN 通过 4-bit BQ 将向量压缩至 2x-8x，尽可能保持向量精度和降低内存占用的同时，减少了极致压缩下复排产生的磁盘开销。

<图/桶索引落盘结构>

如果桶内向量数量小于等于 T，桶索引除了保留量化向量外，头部记录了 3 个 8 字节字段，分别是桶索引对齐的向量维度以用于快速线性扫描、每维的量化位宽以驱动扩展码计算和桶内的向量数量，桶内内容除了包含将 32 个向量打包为一批的 1-bit code，用 1 字节数组保存经列优先重排后以匹配 SIMD 的 shuffle 查表，用于批量线性扫描计算 1-bit 维度的近似点积；还保留了长度为向量数量的浮点数组记录每个向量的加性因子和缩放因子，用于最终在 1-bit 距离计算基础上的额外扩展 bit 距离估计。

如果桶内向量数量大于 T，先用原始的高精度向量构建完整 Vamana 图，以精确反映桶内向量空间真实拓扑结构后，再序列化时再将原始精度的图节点替换为 BQ 量化后的向量，既保证了图索引的精度，又减少了索引查询时访问该图索引所需要的内存。相比桶索引，图索引的头部还记录了图的度数，桶内内容则额外保存了每个图节点的邻居 id，由于桶内数量限制，4 字节的 ID 大小便能记录约 4G 数据量的图结构。

为进一步减少构建图索引的开销，使用 SQ 压缩后的向量再构图，可以在加速图构建的同时尽可能地保证图结构的完整性，除此外构图时需要注意图索引的可达性，即对于没有入度的孤儿节点，需要额外加边以确保该节点可达。

### S.2.2 索引查询

索引查询时，通过对比查询向量和所有质心向量的距离，若质心数量超过 T 时，构建常驻内存的原始精度 Vamana 图，筛选确定距离查询向量最近的 F 个桶后，将这 F 个桶的桶索引或图索引放置到内存中进行桶搜或图搜得到候选向量后，根据候选向量的全局 ID，将符合一个读粒度的顺序 ID 打包为一个磁盘读，以减少重复的磁盘读。



## S.3 无锁异步查询任务流水线

基于磁盘内存混合的向量索引的性能瓶颈很大部份源于磁盘的访问性能，虽然大幅降低了内存占用，但过长的磁盘延时导致实际查询性能非常差，LiteANN 通过解耦桶内索引的计算任务和 I/O 任务，通过带优先级的异步流水线处理重叠的计算任务和 IO 任务，充分发挥计算资源计算性能的同时，降低磁盘访问导致的 I/O 等待，提升 I/O 处理效率。

### S.3.1 查询的三阶段划分

LiteANN 查询索引过程先遍历内存内所有的聚类质心获取真实距离最近的 F 个桶后，将这 F 个桶内索引放置在内存中，遍历索引获取近似距离最近的 S 个候选向量，再对比查询向量与这 S 个候选向量在磁盘内的高精度向量的真实距离后，返回距离最近的前 K 个向量。

可以将该查询过程分为三个阶段，第一阶段是根据聚类质心获取对应桶索引，第二阶段是根据桶内索引获取最近候选向量，第三阶段是根据候选向量获取高精度向量用于复排。其中，第一阶段有对比聚类质心的计算任务，以及获取磁盘内相应桶索引的磁盘任务；第二阶段仅有遍历图索引或桶索引获取候选向量后，根据候选向量的全局 ID，将邻近全局向量打包为一个磁盘块的读任务交给阶段三；第三阶段得到磁盘读任务返回的候选向量对应的高精度向量后，计算其与查询向量的高精度距离，将距离最近的前 K 个向量加入结果集中。

### S.3.1 固定三阶段的查询流水线

在计算资源丰富的场景下，通过并发所有可用的计算单元能高效地处理多个查询任务，但在内存-磁盘混合场景中却不能将线程的性能全部发挥出来，这与任务间调度的磁盘 IO 阻塞相关。

> Best-parallel search

在 LiteANN 为代表的基于桶的索引查询的三个阶段共有三个顺序的计算任务，两个分别用于计算任务二和计算任务三的磁盘任务，如图 x 所示，灰色、黑色部分为磁盘任务一和磁盘任务二，黄色、橙色和红色为计算任务一、计算任务二和计算任务三，在并行顺序执行过程中，计算任务二和计算任务三在等待磁盘任务一和磁盘任务二时，由于在等待磁盘任务的完成，会出现 CPU 空转的情况，并不能高效地使用 CPU 的全部计算能力，8c 机器上实验时 CPU 的平均利用率仅有 2c 到 3c，近一半以上的计算能力未被利用。

容易想到，通过解耦计算和 I/O 任务，在等待磁盘任务完成时，调度空闲 CPU 去完成流水线上其他的计算任务即能充分利用 CPU 资源，通过将各阶段的计算任务绑定相应核建立阶段任务池，仅负责处理该任务池的任务以减少线程切换的开销。如计算任务一对应的 stage_1 任务池，当 stage_1 任务池有空闲任务时，则调用线程池资源快速处理，如图 x 所示，以重叠计算任务和 I/O 任务的方式能最大效率减少 CPU 空等的时间。

> pipeline search

而该方法在实验中仅是将原有 25%~37% 的 CPU 资源利用率提高到了 43%～62% 左右，并且导致了 CPU 资源的较大的抖动，该原因是由于系统积压大量重排任务时，stage_3 任务池内所有线程都在满负荷工作，待处理的任务队列可能很长，而同时 stage_1 和 stage_2  由于没有后续新的查询，CPU 处于空闲状态导致相应资源被限制；其次，需要为三个任务池分别分配相应线程数，分配的比例是可学习的参数，但难以确定最优的配置参数。

### S.3.2 带优先级的异步两阶段流水线

为能更进一步地最大效率利用 CPU 计算能力，LiteANN 采用一个逻辑上依然分为三个阶段，但由统一计算资源池和磁盘 I/O 存储资源池执行的物理两阶段流水线架构。

> 异步两阶段流水线

该架构如图 x 所示，将计算任务依次分配优先级，即优先处理计算任务三，再处理计算任务二，最后处理计算任务一的目的是确保流水线末端的任务能被优先处理，减少查询整体延迟；将这些计算任务放置在统一的计算资源线程池内，线程池内所有线程共享，能够执行所有阶段的计算任务。

负责磁盘任务的是独立于计算资源池外的磁盘专用访问线程，其通过 NUMA 亲和绑定在单独的 CPU 核上，该线程的唯一职责是阻塞等待并处理存储资源池内已完成的异步 I/O 事件，然后再将结果推送到计算资源池内，通过单独绑核防止了流水线上在等待 I/O 时无效占用 CPU 计算资源的情况。其中若计算任务一找到的最近 F 个桶内索引不在缓存中，则将获取索引的任务交由存储资源池处理；而对于计算任务二提交的获取高精度向量任务，由于高精度向量存储于磁盘文件内，因此所有计算任务二完成后，都需要向存储资源池提交磁盘任务二，等待磁盘任务二完成后，再将相应高精度向量传递给计算资源池内的计算任务三。

通过该高效异步、CPU 高度亲和的带优先级的异步两阶段流水线，向量索引查询时即使需要查询多个桶内的索引并获取磁盘内多个候选向量的高精度向量，CPU 的实际利用率达到81%~100%，不仅提升了 CPU 的计算效率，还适用于更大规模的计算集群和存储集群。



## S.4 其他优化

### S.4.1 图索引入口点

在对图索引进行搜索时，为避免因为静态入口点而陷入局部最优，在搜索图索引时会选一定数量的图起点确定初始贪心扩展方向。这些图节点从桶内向量中随机选择，使用多起点以有限的计算开销去有效降低了坏起点带来的召回波动。

### S.4.2 邻近 I/O 合并

复排阶段将需要的高精度向量按找全局 ID 排序并合并为尽量连续的磁盘段，以减少磁盘的随机 IO 访问，通过将每个磁盘段对齐到块边界（如 4K），同时控制单个段内向量的数量和段内向量ID的最大冗余间隙以便打包读取后在内存中减少冗余的距离计算数。具体步骤首先对候选向量的全局 ID 升序排序并去重重复 IDs，随后从前向后合并相邻或近邻全局 IDs 为单段，如果下一个全局 ID 与当前段末尾向量的 ID 的间隙差少于最大冗余间隙，并且合并该向量到已有合并段，合并段内向量个数和总字节少于读取最大段的大小后，对每段按照读取粒度（通常 4K）做对齐，从而将多个零散随机 I/O 转化为了少量顺序大块 I/O，显著降低磁盘寻道和系统调用开销。

### S.4.3 MPSC 无锁队列

为高效地处理流水线上的异步多任务，LiteANN 通过线程安全的多生产者-单消费者（MPSC）通道连接跨线程的三阶段任务，以及通过异步IO库（libaio）磁盘管理线程将“读完成”的上下文推送到计算任务三的复排任务队列内。考虑磁盘任务堆积过多时，有可能导致计算资源池内无活跃任务，MPSC 队列内先以非阻塞的 try_pop 快速抢占待做任务，减少任务调度与唤醒开销；当计算资源池内无活跃任务时，短时阻塞任务队列 wait_pop(2ms) 避免 CPU 空转。

任务队列的处理优先级由三个计算任务队列的 try_pop 实现就近处理，以减少队列内任务堆积；如果对这些计算任务队列执行 try_pop 都为空时，依序对这三个队列各做 wait_pop(2ms) 避免长期忙等待，2ms 为短阻塞时延，在低负载或阶段性抖动时通过短阻塞能有效避免忙轮询，削弱尾延迟性能波动。
