# Motivation

## M.1 Graph index performance accorrding to memory

DiskANN 是目前容量型机器最常用的磁盘索引，它将 PQ 码本存于内存，将高精度向量及其图结构存于磁盘中，通过缓存入口点及其邻接节点用于快速启动查询，查询过程中通过维护一个大小为 L 的候选优先队列，同时获取磁盘内 W 个未被访问的高精度向量及其邻居 ID 数组后，根据与查询向量的真实距离与 pq 距离大小判断是否加入结果集和候选队列中。

DiskANN 的内存占用与 PQ 的压缩率相关，PQ 压缩根据向量维度均分为 M 个部分，每部分进行聚类得到 C 个质心向量，一共有 MxC 个质心向量，这些质心向量则是 PQ 向量的量化表，构建时将向量根据PQ量化表压缩为 PQ 向量后，查询时再将  PQ 向量常驻于内存，得到 PQ 向量与查询向量的近似距离后再判断是否加入到候选队列中。

> 图 x

PQ 压缩率虽然降低了内存占用，但也导致查询的精度不足而需要增大候选队列长度才能获取到足够准确的结果集。如图 x 所示，通过将 Gist-1M 数据集（960 维浮点向量）分别压缩为 320B 和 32B ，并使用相同大小内存缓存入口点及热点向量，测试得到在减少了 56%～2.27x 内存占用下，达到 96% 召回率时 QPS 性能相差了 86.6%~1.02x，并且在更低内存占用下为达到 99% 的召回率，QPS 降低到 100 以下，查询延迟增加严重。

因此，使用 DiskANN 为代表的图索引，虽然降低了内存占用，但同样损失了查询性能。并且随着数据量增加，使用相同的 PQ 压缩，需要的内存占用与数据量增加的趋势线性相关，导致存储成本线性增加，所以仅使用图索引并不适用于数据增长快、内存成本高的场景。

## M.2 Balanced buckets causes longer search latency

SPANN 通过平衡聚类将向量分散到多个大小相等的桶内，避免某个桶内因为数据量过多造成的计算开销过大问题；并根据 RNG 性质将桶间的边缘向量放置在多个桶内，解决由于查询向量由于位于桶间边缘，而无法准确访问到最近的向量桶的数据漂移问题。

> SPANN 图 x

尽管 SPANN 将向量分散在多个桶以减少单个桶的计算开销，但如图 x 所示，为了获得更高的召回，SPANN 需要访问更多的桶以获取到最近邻向量，导致其获取磁盘内单个桶的延迟远高于计算单个桶内向量的延迟，并且由于其桶内向量数量的平衡限制，进一步导致向量被分配时不一定落在其最近桶的概率增大。

> LiteANN 图 x

LiteANN 同样采用 SPANN 相同的处理边缘向量的方法，即将边缘向量根据 RNG 性质放置到最近的 L 个桶内，但仅限制桶内可容纳的最大向量数量，如图 x 所示在 99% Recall@10 下查询向量访问次数最多的前 50 个桶大小分布，可以注意到最大桶被访问的占比为 60%，这说明查询访问与向量分配时都趋近于数据集内更密集的聚类，而平衡聚类强制地将聚类的局部性变弱，即使其通过边缘向量弥补局部性，却增加了为满足高召回而增加桶访问的磁盘延迟，而可以通过仅限制最大桶内的向量数量，既避免了访问单个桶或多个桶内向量超出内存限制，还尽可能地保留了聚类的密集性。

## M.3 Trade-off between Bucket Search and Graph Search

图搜通过贪心策略或其他启发式规则在图上搜索以逐渐逼近查询向量的最近邻，避免了对整个数据集的全量扫描，但受限于图索引的访问顺序性，即每一步搜索都依赖于上一步的计算结果，导致其搜索过程是由计算少量候选节点的距离和从内存中加载下一个节点的向量数据交织进行的，这种随机、零散的内存访问模式极易导致缓存未命中，使得 CPU 花费大量时间等待数据从主存中加载，无法充分发挥其峰值计算性能，即使通过波束搜索（Beam Search）一次性评估多个候选向量，但其依旧无法尽可能地发挥 CPU 的并发计算效率。

桶搜通过计算一个查询向量与桶内所有 N 个向量的距离，由于对这 N 个向量的距离计算是完全独立、互不依赖的，因此可以充分地将这 N 个计算任务分配给空闲的计算单元并行批量处理，不仅能够最大化计算单元的利用率，并能通过连续的内存访问有效利用内存带宽，减少缓存未命中的惩罚。但桶搜固有的线性复杂度 O(N) 带来了严重的可扩展性瓶颈，当 N 增长到一定规模时其查询延迟会急剧增加，因此只能在桶内数据较少时使用桶搜。

如图 x 所示，在 sift 和 gist 数据集的不同数据量下，通过对比在 vamana 图上达到 99% 召回性能的QPS 和 SIMD 优化后的桶搜的 QPS 性能，得到在 10K 到 50K 数据量时，图搜的性能要优于桶搜；同时也注意到，图搜相比桶搜的性能提升在高维场景下提升比例没有低维明显，这是由于高维场景下，桶搜的顺序内存访问和 SIMD 向量化使得计算密集度随着维度上升而更能发挥计算资源的并行效率。因此根据桶内的数据量再进一步选择构建桶索引或是图索引，能充分发挥两类索引在不同数据量下的查询效率，而在任何数据量下，能充分地利用空闲的计算资源都是提升向量相似性检索性能的关键因素。
